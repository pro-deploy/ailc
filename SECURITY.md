# Политика безопасности ailc

## Поддерживаемые версии

Исправления безопасности выпускаются для последней опубликованной минорной версии.
Пользователям более старых версий рекомендуется обновиться перед обращением.

## Как сообщить об уязвимости

Не открывайте публичную задачу (issue) для сообщений об уязвимостях. Публичное описание
до выхода исправления подвергает риску всех пользователей продукта.

Направьте сообщение на адрес электронной почты maxbirkin@gmail.com с темой, начинающейся
со слова «security». Если платформа GitHub предоставляет для репозитория механизм частного
сообщения о уязвимости (Private vulnerability reporting), допустимо воспользоваться им.

В сообщении просим указать затронутую версию продукта и операционную систему, описание
уязвимости и её последствий, порядок воспроизведения (по возможности минимальный пример),
а также ваши пожелания по упоминанию авторства в примечаниях к выпуску.

## Сроки

Подтверждение получения сообщения направляется в течение трёх рабочих дней. Первичная
оценка серьёзности и план действий сообщаются в течение десяти рабочих дней. Исправление
критических уязвимостей выпускается вне очереди, прочих в ближайшем плановом выпуске.

Мы придерживаемся согласованного раскрытия: подробности публикуются после выхода
исправления, по согласованию с сообщившим.

## Область действия

К уязвимостям продукта относятся: выполнение произвольного кода при обработке
проверяемого репозитория, чтение или запись файлов за пределами корня проверяемого
проекта, обход проверки целостности при установке, а также любые дефекты, позволяющие
выдать непройденный вердикт за пройденный.

К уязвимостям продукта не относятся: находки, которые ailc сообщает о ЧУЖОМ коде
(это его штатная работа), а также ложные срабатывания и пропуски правил, для которых
следует открывать обычную задачу.

## Проверка подлинности поставки

Артефакты выпуска сопровождаются контрольными суммами SHA-256. Установщики и обёртка для
npm сверяют контрольную сумму до распаковки и прерывают установку при несовпадении либо
при недоступности суммы. Осознанный обход проверки возможен только явной переменной
окружения `AILC_INSECURE_SKIP_CHECKSUM=1` и в обычной работе применяться не должен.

Криптографическая подпись артефактов пока не выполняется, поэтому контрольная сумма
подтверждает целостность загрузки, но не подлинность источника. Введение подписи
запланировано, см. задачу T-03 в файле [ЗАДАЧИ.md](ЗАДАЧИ.md).
